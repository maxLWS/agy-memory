## 1. 评测方法与公平性控制

为了避免纸面微基准掩盖真实 Agent 行为问题，所有端到端数据均来自真实无头 `agy` 进程（`agy -p --output-format json --dangerously-skip-permissions --print-timeout 180s`）：

- **冻结语料快照**：基于 **139 条本机真实历史会话**（70 条主会话 + 69 条子代理/Swarm worker 会话；约 `50 MB` `transcript.jsonl`、`~99 MB` `transcript_full.jsonl`、Markdown Artifacts 与多成员 Swarm 留言板）制作只读硬链接快照，并排除本次开发与评测会话，杜绝信息泄漏。
- **严格环境隔离**：每项任务都在独立临时 `HOME` 中运行。Baseline 组完全不挂载 `agy-memory`（`0` 次快照注入、`0` 次记忆工具调用）；实验组挂载已安装的 `agy-memory`（`7/7` 快照注入）。每轮结束后核验本机真实 `conversation_summaries.db`、`brain/` 与 `notes.json` 均 0 改动。
- **固定模型与提示词**：Baseline、`v0.1.0`、`v0.2.0` 全程固定同一模型（`gemini-3.8-flash-medium`）与逐字节一致的用户提问。
- **客观程序判分**：每题均设可验证的事实断言（目标会话定位、核心结论、Artifact 路径、Swarm 成员结论、跨会话笔记持久化、负例不产生幻觉）。
- **指标复算校验**：所有 token、轮次、工具调用与溢盘数均直接从 24 份原始 `transcript.jsonl` 重新统计并与 `agy --output-format json` 对齐（0 偏差）。估算计费等效 Token 按保守权重计算：
  ```
  est_billable_equiv = uncached_input + 0.1 * cache_read + 5 * output
  ```

## 3. 第一轮暴露出的 3 个真实问题与 `v0.2.0` 根治方案

如果只跑单元测试，这三个问题完全不会暴露；跑真实 `agy` 端到端对话后全部原形毕露：

### 问题 1（P0）：当前会话自匹配导致 T7 负例超时失败（`FAIL → PASS`）
- **`v0.1.0` 现象**：用户让模型去历史里查一个不存在的代号，但 `agy` 在调用工具前已经把当前这轮的 `USER_INPUT` 写进了磁盘。结果 `search_sessions` 搜到了**当前对话自己的提问**（`[user #0]`），模型看到唯一命中竟是自己、又不敢确信历史里真没有，于是退回跑了 4 条递归 shell `grep`，触发 2 次溢盘并撞上 180s 超时。
- **`v0.2.0` 根治**：
  1. `SessionStart` 开场快照直接注入 `Current session: <shortId>`，提示调用检索时传入 `excludeSessionId`。
  2. `excludeSessionId` 支持 `>=4` 位短前缀和逗号分隔多 ID。
  3. 即使模型忘传 `excludeSessionId`，只要未显式指定 `sessionId`，`search_sessions` 也会自动跳过正在进行中的无回复提问（180s 内无助手回复的最后一条 `USER_INPUT`）。
  4. 0 命中时明确回报扫描覆盖范围（`No past conversations matched "..." (searched N session(s) across transcripts, artifacts, and swarm boards)`）。
- **复测结果**：T7 从 **188.0s 超时失败** 变为 **33.4s 通过（墙钟 -82%）**，原生 shell **0 次**，溢盘 **0 次**，返回体积 **0.8 KB（较基线 -94%）**。

### 问题 2（P0）：Swarm 留言板正向截断切掉最新结论（T3 耗时 `-71%`、Token `-64%`）
- **`v0.1.0` 现象**：面对 85+ 条消息的长 Swarm 留言板，`read_session(mode="swarm")` 按从旧到新顺序拼接后在 8,650 字节处截断——**把最新的 `#66–#85` 结论全切掉了**；而且在 `members.json` 缺失时给不出成员列表，也不支持 `startSeq`/`endSeq`/`query` 过滤。模型调一次 MCP 没看到结果，被迫写 8 条 shell 脚本去硬解析 `board.jsonl`（3 次溢盘、11 轮、83.3s、121.3k 等效 token，比基线还贵）。
- **`v0.2.0` 根治**：
  1. `read_session(mode="swarm")` 改为**从最新消息倒推装入预算**，确保最新结论永不被截断。
  2. 缺少 `members.json` 时自动从 `board.jsonl` 推导 `Board agents` 名单。
  3. 新增 `startSeq` / `endSeq` / `query` 过滤（`tailMessages` 上限 100），并给 `search_sessions` 增加单会话内检索参数 `sessionId`。
- **复测结果**：T3 从 **83.3s / 11 轮 / 8 次 shell / 3 次溢盘 / 121.3k Token** 降到 **24.3s（-71%）/ 3 轮（-73%）/ 0 次 shell / 0 溢盘 / 43.4k Token（-64%）**。

### 问题 3（P1）：大 Artifact 分页冗余与冷路径延迟
- **`v0.1.0` 现象**：
  - T4 检索 Artifact 只返回片段不给完整路径和行数，导致多耗一轮 MCP 分页（`31.1s / 4 轮` 反超基线的 `22.8s / 3 轮`）。
  - 139 条会话微基准剖析显示：每次拉目录都 fork `python3`（`~30–69 ms`），每次检索都重读 6 MB 原始 `transcript.jsonl`（其中 `97.4%` 是工具返回噪音），导致单次检索 `~210 ms`。
- **`v0.2.0` 根治**：
  1. Artifact 命中直接附带行数和完整 `Path`，规则引导 >100 行的 Markdown 报告直接交回内置 `read_file(Path)` 一次读完（46 KB 内联、`~7 ms`）。
  2. 只读 SQLite 改为 `Node 22.5+ 内置 node:sqlite → sqlite3 -readonly -json → 跨平台 Python → 纯 JS 扫描` 四级链路，叠加按 `(db, db-wal, brain)` mtime/size 校验的进程内缓存与解析文档 LRU 缓存。
  3. 自动从 `transcript_full.jsonl` 回填 `truncated_fields` 长回复，并为 >8.2 KB 单轮提供 `charOffset` 续读。
- **实测微基准变化**（139 条冻结语料）：
  - `SessionStart` 钩子：`101.5 ms → 44.0 ms`
  - 热态 `list_sessions`：`38.2 ms → 1.1 ms`
  - 冷态中英 `search_sessions`：`210.4 ms → 59.8 ms`（热态 `20.0 ms`）
  - 3,456 步（6.3 MB）长会话热态 `read_session(digest)`：`79.5 ms → 7.1 ms`
  - T4 从 `31.1s / 4 轮 / 8.4 KB` 降至 `24.9s / 3 轮 / 4.8 KB`。

## 4. 固定开销与适用边界（诚实说明）

- **静态提示词税**：`rules/AGENTS.md` + 5 个 eager 工具 schema + `SessionStart` 开场快照会在首轮增加约 **3,130 input tokens**（受控实测从 `18,093` 增至 `21,223`）。第 2 轮起前缀命中缓存，每轮摊销约 310 等效 token。
- **回本点**：只要在整条对话里省掉 **1 次** 盲目 `grep` / `sqlite3` 探索（通常消耗 `20k–45k` 等效 token 与 `10–20s` 耗时），收益就是整条会话固定开销的 6–14 倍。
- **不需要开启的场景**：完全不涉及过往对话或长期笔记的一次性独立编码任务，会承担少量首轮缓存前缀成本。如果只想在特定项目启用，可以用项目级安装：`node scripts/install.mjs install --project /path/to/repo`。

## 五、`v0.3.0` 实测数据与已知边界

`v0.3.0` 新增了文件/报错历史检索、Markdown 笔记和只读 Codex/Claude 会话支持，保持 5 个工具和零运行时依赖不变，同时把启动元数据（5 个 Schema + `rules/AGENTS.md`）从 `v0.2.0` 的 `11,022 B` 压到了 `7,668 B`（`-30.4%`）。

1. **核心回归（T1–T7，同冻结 139 会话快照，`n=1`）**：`7/7` 通过（模型耗时 `208.7s` / 墙钟 `260.7s` / `29` 轮 / 估算计费 `375,011`，与 `v0.2.0` 的 `213.2s` / `270.4s` / `30` 轮 / `373,734` 基本持平）。初版在 T7 出现 2 次溢盘，在 `text` 模式 0 命中返回补上完整扫描提示后，复测 T7（`n=2`）恢复为 `0` 溢盘 / `4` 轮 / `44,846` 计费。
2. **文件写读核验（`mode="file_history"`）**：在给出候选会话 ID 区分修改与只读的任务上（`n=1`），`v0.3.0` 用 `21.6s` / `3` 轮 / `44.5k` 计费 / `0` 溢盘完成，关闭 trace 后为 `122.0s` / `14` 轮 / `158.3k`（`v0.2.0` `90.0s` / `12` 轮，基线 `113.5s` / `14` 轮）。不给候选 ID 的盲查复测（`n=2`）同样 `2/2` 通过并首轮走 `file_history`（7 轮与 23 轮）。
3. **命令报错回溯（`mode="error_history"`，`n=5` 随机配对）**：初版首轮默认走 `mode="text"`（`4/5` 通过，中位 `78.2s` [区间 `54.7–190.2s`]、`10` 轮、`92.1k` 计费、总计 `15` 次溢盘）。在 `mode` 参数描述和 0 命中返回里加上明确的路由提示后，配对重测达到 `5/5` 通过、`5/5` 首轮直达 `error_history`、中位 `21.6s` [区间 `18.9–25.7s`]、`2` 轮、`31.3k` 计费 [区间 `29.8k–37.2k`]、`0` 溢盘。带文件名的未见改写题（`n=3`）`3/3` 通过（中位 `35.4s`、`4` 轮、`0` 溢盘）；不给精确文件名的模糊中文提问（`n=3`）同样 `3/3` 先走 `error_history`，但当模型把中文修饰词和英文关键字一起做 AND 查询时仍需额外重试。
4. **跨 CLI 召回（`source="all"`，冻结的真实 Codex + Claude 会话，`n=1`）**：`v0.3.0` 用 `21.9s` / `3` 轮 / `39.1k` 计费 / `0` 溢盘完成，对比无插件基线 `56.3s` / `8` 轮 / `79.5k` 与 `v0.2.0` `134.9s` / `19` 轮 / `192.3k`。
5. **Markdown 笔记（`topics/*.md` + `MEMORY.md`，约 450 B 小笔记，4 组各 `n=1`）**：4 种存储/快照组合全部通过，小笔记上 Markdown 相对旧 JSON **没有省 token**，它的实际价值在人工可直接编辑、修订版本防覆盖和大笔记直调 `read_file`。
6. **无关任务首轮输入开销（`T12`，1 轮，0 次记忆调用）**：首轮输入 token 为基线 `18,222`、`v0.2.0` `22,129`（`+3,907`）、`v0.3.0` `21,496`（较基线 `+3,274`，较 `v0.2.0` 少 `633`）。
7. **独立进程大文件流式压测**：55 MB 单转录（10 万+ 步，目标写入在 52 MB 处）在 32 MB 预算下 `484 ms` 返回 `INCOMPLETE SCAN`，第二次同预算从 32 MB 续扫到 55 MB 用时 `355 ms` 命中目标（峰值 `VmHWM = 119.5 MB`）；12 MB（4 行各 3 MB 超长单行）流式解析用时 `90.5 ms`（`VmHWM = 88.4 MB`）。
